# 页面受控接入指南

适用于希望由一体化平台管理用户能进入哪些业务页面的接入方。平台登记模式为 `PAGE_CONTROLLED`（页面受控）。例如客户已有订单页和报表页，需要在平台分别给不同岗位分配这两个页面的访问权限。

## 1. 开始前先认识三个组成部分

**一体化平台门户**提供统一登录页面。**平台认证服务**在用户登录后，根据客户端登记信息发放一次性授权码。**客户端系统**是要接入的业务系统，由它的后端接收授权码、核对身份并处理本地会话。随文提供的 **示例客户端**是一套用于练习和移植的代码。完整登录需要一个可用的一体化平台环境。

本模式下，平台在确认用户身份时还会检查指定页面的访问许可。平台管理员管理页面权限和角色分配。客户端系统负责让页面入口和相关数据接口都经过后端检查，订单查询范围、导出操作等业务规则也由客户端系统继续执行。

## 2. 登记客户端、页面和角色

先与管理员确认平台门户和认证服务可用，并为本次测试使用独立的客户端登记。浏览器还需要能访问平台门户。

1. 接入方提供系统名称、浏览器访问的系统地址，以及一个固定回调路径。本例用 `http://localhost:18085` 和 `/api/auth/callback`。回调是登录完成后由浏览器访问的客户端后端入口。
2. 平台管理员创建并启用客户端，登记相应认证模式和上述地址，交付客户端编号 `client_id`、客户端密钥 `client_secret`、平台认证接口前缀和测试账号。
3. 登录测试前核对完整回调地址。例如 `http://localhost:18085/api/auth/callback` 必须与平台登记组合及客户端配置一致，包括协议、主机、端口和路径。客户端密钥由管理员创建或重置时取得，交给接入方后端负责人保管。

在平台选择页面受控。先登记拟接入的真实页面地址，再为每页确定唯一的页面编码。以下三个页面可以直接用于示例。正式接入时，用自己的页面路径和约定编码替换演示值。

| 页面 | 页面编码 `page_code` | 页面路径 | 权限项示例 |
| --- | --- | --- | --- |
| 订单查询 | `B_PAGE_01` | `/pages/orders` | `b:orders:view` |
| 经营报表 | `B_PAGE_02` | `/pages/reports` | `b:reports:view` |
| 运维控制台 | `B_PAGE_03` | `/pages/operations` | `b:operations:view` |

由平台管理员在客户端的页面配置中登记并启用这些页面。管理端若自动创建权限项，应使用实际生成的权限。若需手工创建，则以实际权限标识登记。接着在【角色管理】的【外部系统页面权限】中，为测试账号所属的普通角色勾选订单页。确认测试账号的其他角色也未分配报表页权限，才能稳定核对拒绝结果。管理菜单名称以部署版本为准。

## 3. 先用示例确认页面可进和不可进

从仓库根目录将 `.env.example` 复制为 `.env`，已有 `.env` 时编辑现有文件。按 `键=值` 格式填写，替换下面的地址、编号和密钥示例。示例的浏览器导航和后端调用使用同一个 `SSO_BASE_URL`，两边都要能访问。把 `SSO_BASE_URL` 换成管理员提供的公共认证接口前缀，通常以 `/oauth2Server/oauth2` 结尾。认证接口地址与门户登录网页地址分别由管理员确认。

```properties
SSO_BASE_URL=http://localhost:19089/oauth2Server/oauth2
SSO_CLIENT_ID=替换为平台分配的客户端编号
SSO_CLIENT_SECRET=替换为平台交付的明文密钥
B_CALLBACK_URL=http://localhost:18085/api/auth/callback
SSO_AUTH_MODE=PAGE_CONTROLLED
SSO_REQUIRE_EXTERNAL_ACCOUNT=false
```

示例将真实密钥和平台访问令牌保存在后端。浏览器通过本地会话标识识别登录状态。一次性授权码和校验值会经过浏览器回调地址，由客户端后端处理。

运行示例需要 JDK 8、Maven 和符合 `frontend/package.json` 要求的 Node.js（22.18 起的 22.x，或 24.12 及以上）。在仓库根目录执行：

```powershell
.\scripts\package.ps1
java -jar backend/target/sso-client-b-demo-0.1.0-SNAPSHOT.jar
```

Linux 或 macOS 将第一条换为 `bash scripts/package.sh`。浏览器打开 `http://localhost:18085`，首页出现“业务系统 B”表示示例启动成功。点击业务页面才会开始与平台认证服务交互。把示例部署到别的机器时，回调中的 `localhost` 也要换成浏览器实际访问的主机。

1. 打开【订单查询】并登录。授权请求应关联 `B_PAGE_01`。固定回调完成后进入订单页，刷新时后端继续核验该页授权。
2. 返回首页，打开【经营报表】。如果账号未分配报表权限，本次访问应被拒绝。直接在地址栏输入 `/pages/reports` 也应得到相同结果。示例首页列出的链接来自演示目录，实际是否放行以服务端检查为准。
3. 请平台管理员分配报表页权限，从业务入口重新访问。订单页和报表页各使用自己的授权。再取消其中一页的角色权限，下一次受保护请求应被拒绝。

## 4. 把页面访问控制接到自己的系统

### 4.1 先为一个真实页面建立后端入口

| 改造位置 | 示例代码 | 需要实现的行为 |
| --- | --- | --- |
| 页面路径与编码 | `auth/PageCatalog.java` | 按受信任的后端路由找到页面编码，避免由浏览器决定所需权限 |
| 业务页面和数据检查 | `demo/PageController.java`、`auth/PageAccessService.java` | 发起该页授权，通过平台核验后再执行业务检查 |
| 固定回调和授权存储 | `auth/AuthController.java`、`auth/LoginStateStore.java`、`auth/PageTokenStore.java` | 所有页面共用一个回调，按会话和页面分别保存授权 |
| 与平台交互 | `config/SsoConfig.java`、`sso/SsoClient.java` | 授权时传 `page_code`，核验时传 `pageCode`，核对返回的客户端、页面和用户 |

上述代码路径相对于 `backend/src/main/java/com/dcs4/ssoclient/`。对于已有业务系统，保留自己的页面和权限代码，把相同的校验放在后端页面和接口入口。

### 4.2 以订单查询为例串起完整流程

1. 访问 `/pages/orders` 时，客户端后端根据路径确定页面编码 `B_PAGE_01`，并读取当前会话下该页的授权。
2. 没有可用授权时，后端生成 `state`（与当前会话绑定的一次性随机校验值），保存订单页作为本次回跳目标，浏览器进入带 `page_code=B_PAGE_01` 的平台授权地址。
3. 平台检查该用户是否有此页权限。允许时返回授权码至固定回调。客户端后端消费 `state`、兑换授权码，核对授权所属客户端、用户和页面，再访问 `/checkAccessToken` 校验。校验通过后，通过用户信息接口核对当前用户处于启用状态，再保存订单页自己的授权、更新本地会话并回到订单页。平台返回拒绝时结束本次请求，展示无权限结果。
4. 页面打开后，订单列表、详情、导出等接口也在后端核对相应页面授权，并按业务系统规则控制能够查询哪些订单、能否导出。报表接口应使用报表页自己的授权。现有示例的库存接口扩展代码位于 `docs/examples/InventoryApiController.java`，按需参考。

移植时将平台访问令牌放在服务端，在刷新时成对更新访问令牌与续期令牌。同一组令牌的刷新应按会话和授权范围串行执行。示例使用单实例内存会话。若客户端系统部署多实例，应让原始登录请求与回调能读到同一份登录状态，并处理并发刷新和节点故障后的重新授权。

认证服务超时或返回未知结果时，当前业务请求应返回错误，用户可以在服务恢复后重试。后端校验与前端展示应按同一个账号更新，切换账号时清理上一账号留在本地会话中的授权。

在现有前端中，页面入口可以通过浏览器整页跳转完成登录。数据接口需要登录时，可返回明确的状态及由后端生成的登录地址，由前端发起整页跳转。前端菜单、按钮及路由的可见性负责展示，业务接口的放行条件由后端执行。

### 4.3 接上退出入口

本地退出由客户端后端清理本系统会话，并用服务端保存的授权凭据向平台撤销本客户端相应授权。示例入口为 `POST /api/auth/logout/system`。全局退出可参考 `POST /api/auth/logout/global`，客户端先处理本地退出，再将平台退出地址交给浏览器整页打开。平台退出后的回跳地址应与已登记客户端地址同源。示例的提交请求带同会话的 CSRF 校验值，用于防止其他网站代替用户发起操作。

### 4.4 按订单页请求定位代码

| 要找的环节 | 具体代码位置 |
| --- | --- |
| 页面路径从哪里映射到编码 | [PageCatalog.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/PageCatalog.java) 的构造方法登记订单页，`requireByPath()` 根据后端收到的页面路径取出编码 |
| 一个业务页面如何受控 | [PageController.java](../../backend/src/main/java/com/dcs4/ssoclient/demo/PageController.java) 的 `page()` 接收 `GET /pages/orders` 并调用 [PageAccessService.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/PageAccessService.java) 的 `enter()` |
| 平台调用在哪里带上页面编码 | [SsoClient.java](../../backend/src/main/java/com/dcs4/ssoclient/sso/SsoClient.java) 的 `authorizeUrl()` 添加 `page_code`，`checkAccessToken()` 添加 `pageCode` |
| 多个页面怎样共用固定回调 | [AuthController.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/AuthController.java) 的 `callback()` 接收 `GET /api/auth/callback`。`completeCallback()` 用服务端保存的登录请求确定页面，核对令牌再保存 |
| 页面授权为什么分别保存 | [SsoConfig.java](../../backend/src/main/java/com/dcs4/ssoclient/config/SsoConfig.java) 的 `tokenKey()` 在页面受控模式下返回页面编码，[PageTokenStore.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/PageTokenStore.java) 保存对应授权 |
| 怎样保护页面的数据接口 | [InventoryApiController.java](../examples/InventoryApiController.java) 的 `inventory()` 用后端登记的库存页面发起校验。新增自己的接口时，沿用同样的页面映射，并在查询数据前执行本地业务权限检查 |
| 如何退出指定页面或整个系统 | [AuthController.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/AuthController.java) 的 `logoutPage()`、`logoutSystem()` 和 `logoutGlobal()` 分别对应三种退出范围 |

## 5. 部署地址与反向代理

以下是跨机部署示例。假设一体化平台和 Nginx（反向代理服务器）在 `192.9.230.24`，客户端实际服务在 `192.9.230.16:18085`。示例端口按现场替换。

| 项目 | 示例值 |
| --- | --- |
| 浏览器打开的客户端系统地址 | `http://192.9.230.24:18085` |
| 平台登记的系统地址 | `http://192.9.230.24:18085` |
| 平台登记的固定回调路径 | `/api/auth/callback` |
| 客户端配置的完整回调地址 | `http://192.9.230.24:18085/api/auth/callback` |
| Nginx 转发目标 | `http://192.9.230.16:18085`，保留原请求路径 |
| 平台认证接口前缀 | 由平台管理员提供，浏览器和客户端后端均需可达 |

在 `192.9.230.24` 的客户端入口上，将首页、静态资源、`/api/` 和业务页面请求转发给 `192.9.230.16`。回调应能直接到达客户端后端，回调后的页面和全局退出跳回的首页应留在同一个对外入口。生产使用 HTTPS（加密网页通信）时，登记和配置均使用浏览器看到的 HTTPS 地址，示例后端同时配置 `COOKIE_SECURE=true`。

在 Nginx 的站点配置中，可以按下面的方式转发客户端流量。示例采用内网 HTTP 地址帮助理解转发关系。

```nginx
server {
    listen 18085;

    location / {
        proxy_pass http://192.9.230.16:18085;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

整页登录跳转可以跨来源。只有前端脚本需要直接读取另一个来源的接口，或页面需要共享同一来源时，才需要专门处理同源问题。同源要求协议、主机和端口一致。只改为同一个 IP、仍开两个端口，浏览器依然会区分来源。示例中的首页、静态资源和绝对路径回跳以站点根路径为基础。若改成同一入口下的 `/client/` 前缀，应同步适配静态资源、业务路径、固定回调、会话标识发送范围和退出回跳。

上线前，检查代理、网关和应用日志。固定回调查询串会带一次性授权码与校验值。访问日志只记路径和必要的状态信息，例如在 Nginx 日志格式中用 `$uri` 记录路径。避免记录完整回调地址、认证请求正文或会话标识。

如果门户要提供业务菜单入口，菜单地址指向客户端系统的受保护页面或后端入口。客户端还要确保用户访问页面、数据接口或原始服务地址时，后端始终执行访问检查。若旧系统无法改造，需要另行设计能保护页面、接口和原始服务的接入层。

## 6. 接入完成后先核对这些结果

第 3 节可用示例观察页面授权。下面核对的是接入方自己的系统，验收时请同时访问实际业务页面和它的数据接口。撤销页面权限时，需确认测试账号已没有其他角色授予该权限。

| 场景 | 预期结果 |
| --- | --- |
| 已分配订单页权限 | 登录后进入订单页，可以使用业务系统允许的操作 |
| 未分配报表页权限 | 进入报表页被拒绝，直接访问报表路径或接口同样受检查 |
| 同一用户拥有两个页面的权限 | 分别取得两份页面授权，访问时核验当前页 |
| 平台撤销某页权限 | 下一次访问该页或对应接口时被拒绝。已经显示的页面需通过新请求反映变化 |
| 退出单页或整个客户端 | 单页退出移除本地对应授权并向平台请求撤销。整个客户端退出结束本地会话，并请求撤销本客户端保存的全部授权 |
| 全局单点退出 | 平台登录状态失效，再访问时需重新登录并获得相应页面权限 |

被拒绝时，依次核对两端的模式、页面路径及编码、平台实际授权的权限项和测试账号所属角色。登录后出现 404 或找不到登录事务时，核对代理是否保留路径，以及完整回调是否回到开始访问时的客户端入口。
