# 普通单点登录接入指南（平台维护外部账号绑定）

适用于需要由一体化平台集中维护“平台用户对应哪个本地账号”的系统。平台登记仍选 `SSO_ONLY`（普通单点登录），另外启用外部账号必绑。平台负责管理对应关系和接入资格。客户端系统继续管理本地账号、角色和数据权限。

## 1. 开始前先认识三个组成部分

**一体化平台门户**提供统一登录页面。**平台认证服务**在用户登录后，根据客户端登记信息发放一次性授权码。**客户端系统**是要接入的业务系统，由它的后端接收授权码、核对身份并处理本地会话。随文提供的 **示例客户端**是一套用于练习和移植的代码。完整登录需要一个可用的一体化平台环境。

以张三为例，平台上的用户编号为 `9001`，客户端系统中的本地用户编号为 `108`。平台管理员登记这两个编号的对应关系。张三从业务入口登录时，平台先检查对应关系。缺少有效绑定时，平台会在签发授权码前拒绝本次客户端授权，门户登录仍有效。绑定有效时，客户端后端可从平台用户信息接口取得 `9001` 和 `108`，并以本地账号 `108` 处理本系统的角色、待办和历史数据。

如果客户端系统希望自行维护这条对应关系，应使用普通单点登录并关闭平台必绑。以下步骤适用于双方已明确由平台管理对应关系的情况。

## 2. 双方先准备测试账号，再登记绑定

先与管理员确认平台门户和认证服务可用，并为本次测试使用独立的客户端登记。浏览器还需要能访问平台门户。

1. 接入方提供系统名称、浏览器访问的系统地址，以及一个固定回调路径。本例用 `http://localhost:18085` 和 `/api/auth/callback`。回调是登录完成后由浏览器访问的客户端后端入口。
2. 平台管理员创建并启用客户端，登记相应认证模式和上述地址，交付客户端编号 `client_id`、客户端密钥 `client_secret`、平台认证接口前缀和测试账号。
3. 登录测试前核对完整回调地址。例如 `http://localhost:18085/api/auth/callback` 必须与平台登记组合及客户端配置一致，包括协议、主机、端口和路径。客户端密钥由管理员创建或重置时取得，交给接入方后端负责人保管。

在平台选择普通单点登录。请平台管理员确认当前环境支持外部账号绑定。建议在测试客户端完成验证，再在正式客户端开启必绑。

1. 接入方准备启用的本地测试账号，例如 `108`，并把它的**本地用户唯一编号**交给平台管理员。同步约定测试用户当天可访问的业务页面或数据范围。
2. 管理员在该客户端的外部账号绑定配置中选择平台用户 `9001`，录入客户端本地用户编号 `108`，确认绑定后启用必绑。平台管理页面的入口名称以环境为准，页面暂未开放此功能时，由具备权限的平台管理员通过管理接口完成。
3. 准备三名平台测试用户。第一名绑定到示例的启用账号 `108`，第二名绑定到停用账号 `109`，第三名保持未绑定。`108` 和 `109` 仅用于示例。真实系统可按相同方法选择自己的测试账号。正式启用必绑前，先盘点需要保留接入权限的用户并核对对应关系。

若当前平台管理页面没有绑定入口，具备 `common:sys_sso:edit` 权限的管理员可在平台管理端使用接口。先用 `GET /common/sysSso/accountBindings?clientConfigId=登记记录编号` 查看现有设置，再通过 `POST /common/sysSso/accountBindings` 保存。`clientConfigId` 是平台管理列表里该客户端的登记记录编号。请求体包含 `clientConfigId`、`externalAccountRequired`（是否必绑）和完整的 `bindings`（绑定列表）。每条绑定填 `sacUserId`（平台用户编号）和 `externalUserId`（本地用户编号）。保存前确认原有绑定已一并保留，因为服务端会按提交的完整列表更新。

同一客户端下两侧编号都应唯一。一个平台用户在不同客户端可以对应不同的本地编号。维护时以用户编号为准，姓名只用于核对人员。

## 3. 运行示例并核对本地账号

从仓库根目录将 `.env.example` 复制为 `.env`，已有 `.env` 时编辑现有文件。按 `键=值` 格式填写，替换下面的地址、编号和密钥示例。示例的浏览器导航和后端调用使用同一个 `SSO_BASE_URL`，两边都要能访问。把 `SSO_BASE_URL` 换成管理员提供的公共认证接口前缀，通常以 `/oauth2Server/oauth2` 结尾。认证接口地址与门户登录网页地址分别由管理员确认。

```properties
SSO_BASE_URL=http://localhost:19089/oauth2Server/oauth2
SSO_CLIENT_ID=替换为平台分配的客户端编号
SSO_CLIENT_SECRET=替换为平台交付的明文密钥
B_CALLBACK_URL=http://localhost:18085/api/auth/callback
SSO_AUTH_MODE=SSO_ONLY
SSO_REQUIRE_EXTERNAL_ACCOUNT=true
```

将 `SSO_REQUIRE_EXTERNAL_ACCOUNT` 设为 `true` 后，示例按平台返回的本地编号校验本地账号。平台的必绑开关也要开启。示例将真实密钥和平台访问令牌保存在后端。浏览器通过本地会话标识识别登录状态。一次性授权码和校验值会经过浏览器回调地址，由客户端后端处理。

运行示例需要 JDK 8、Maven 和符合 `frontend/package.json` 要求的 Node.js（22.18 起的 22.x，或 24.12 及以上）。在仓库根目录执行：

```powershell
.\scripts\package.ps1
java -jar backend/target/sso-client-b-demo-0.1.0-SNAPSHOT.jar
```

Linux 或 macOS 将第一条换为 `bash scripts/package.sh`。浏览器打开 `http://localhost:18085`，首页出现“业务系统 B”表示示例启动成功。点击业务页面才会开始与平台认证服务交互。把示例部署到别的机器时，回调中的 `localhost` 也要换成浏览器实际访问的主机。

示例内置两个演示账号，`108` 已启用，`109` 已停用。平台绑定时填这两个编号之一。真实系统使用自己的账号服务，账号编号由接入方提供。

1. 使用绑定到 `108` 的平台账号访问【订单查询】。成功后返回示例首页，用户摘要应显示【本地账号编号】为 `108`。该编号来自后端保存的本地会话。
2. 换一个新的浏览器会话，使用绑定到 `109` 的测试用户。平台可完成身份授权，示例后端提示“本地账号未开通或已停用”，业务页面被拒绝。
3. 再以未绑定的平台用户进入。平台在授权阶段拒绝，示例无法创建本地会话。分别用新会话可以避免复用上一个测试账号的登录状态。

## 4. 在客户端后端接入本地账号

### 4.1 在回调中增加账号处理

示例代码路径相对于 `backend/src/main/java/com/dcs4/ssoclient/`。

| 步骤 | 在哪里看参考代码 | 接入方怎样做 |
| --- | --- | --- |
| 发起登录 | `auth/PageAccessService.java`、`sso/SsoClient.java` | 采用系统级授权，省略页面编码，由后端保存 `state`（与当前会话绑定的一次性随机校验值）和原业务目标 |
| 处理固定回调 | `auth/AuthController.java`、`auth/PageAccessService.java` 的 `completeCallback` | 消费 `state`，后端兑换授权码、核对客户端和平台用户、校验访问令牌。收到平台拒绝时结束请求，提示未开通或联系管理员 |
| 读取身份 | `sso/SsoModels.java` 的 `UserInfo`、`sso/SsoClient.java` 的 `getUserInfo` | 取得 `/getUserInfoByOauth2` 返回的 `result.id` 和 `result.externalUserId`。示例用户信息模型以字符串字段 `externalUserId` 接收本地编号 |
| 查本地账号并保存会话 | `PageAccessService.completeCallback` 中身份校验之后、写入本地会话之前 | 调用 `verifyLocalAccount()` 检查本地账号是否存在并启用，成功后保存本地用户编号。移植时用自己的用户服务实现 `LocalAccountDirectory.isEnabled()`，并按本地编号加载业务权限 |

平台用户信息中与本场景直接相关的字段如下。两个编号均按字符串处理。

| 字段 | 示例 | 用途 |
| --- | --- | --- |
| `result.id` | `9001` | 确认平台身份，并与授权结果中的平台用户标识核对 |
| `result.externalUserId` | `108` | 查询客户端系统的本地用户记录 |

先阅读 [LocalAccountDirectory.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/LocalAccountDirectory.java) 的 `isEnabled()`，再看 [DemoLocalAccountDirectory.java](../../backend/src/main/java/com/dcs4/ssoclient/demo/DemoLocalAccountDirectory.java) 如何判断演示账号。移植时，将这个判断接到现有用户服务，查到且启用才返回 `true`。其他登录步骤沿用示例。

```text
平台身份核验通过
  → 读取本地用户编号
  → 检查本地编号和账号启用状态
    · 校验失败：拒绝本次登录
    · 校验通过：更新会话标识，以本地账号建立会话并返回原业务页面
```

本方案要求本地编号有效。遇到字段为空、账号缺失或停用时，应明确拒绝当前登录，避免沿用另一个用户的本地授权。业务页面和数据接口在后端以本地账号判断权限，同时继续核验平台授权有效性。解除或更换绑定后，旧令牌会失效。客户端系统发现授权失效时，应结束相应的本地登录状态并要求从业务入口重新授权。

移植时将平台访问令牌放在服务端，在刷新时成对更新访问令牌与续期令牌。同一组令牌的刷新应按会话和授权范围串行执行。示例使用单实例内存会话。若客户端系统部署多实例，应让原始登录请求与回调能读到同一份登录状态，并处理并发刷新和节点故障后的重新授权。

认证服务超时或返回未知结果时，当前业务请求应返回错误，用户可以在服务恢复后重试。后端校验与前端展示应按同一个账号更新，切换账号时清理上一账号留在本地会话中的授权。

在现有前端中，页面入口可以通过浏览器整页跳转完成登录。数据接口需要登录时，可返回明确的状态及由后端生成的登录地址，由前端发起整页跳转。前端菜单、按钮及路由的可见性负责展示，业务接口的放行条件由后端执行。

### 4.2 接上退出入口

本地退出由客户端后端清理本系统会话，并用服务端保存的授权凭据向平台撤销本客户端相应授权。示例入口为 `POST /api/auth/logout/system`。全局退出可参考 `POST /api/auth/logout/global`，客户端先处理本地退出，再将平台退出地址交给浏览器整页打开。平台退出后的回跳地址应与已登记客户端地址同源。示例的提交请求带同会话的 CSRF 校验值，用于防止其他网站代替用户发起操作。

### 4.3 按请求顺序阅读示例代码

| 要找的环节 | 具体代码位置 |
| --- | --- |
| 业务入口 | [PageController.java](../../backend/src/main/java/com/dcs4/ssoclient/demo/PageController.java) 的 `page()` 接收订单页请求，在业务页面渲染前调用后端检查 |
| 平台用户资料 | [SsoClient.java](../../backend/src/main/java/com/dcs4/ssoclient/sso/SsoClient.java) 的 `getUserInfo()` 调用 `POST /getUserInfoByOauth2`，用 [SsoModels.java](../../backend/src/main/java/com/dcs4/ssoclient/sso/SsoModels.java) 的 `UserInfo` 接收资料 |
| 本地账号判断放在哪里 | [PageAccessService.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/PageAccessService.java) 的 `completeCallback()` 在平台身份核验通过后调用 `verifyLocalAccount()`。`enter()` 在后续请求中核验本地账号和平台授权，`currentLocalUserId()` 读取已确认的本地编号 |
| 客户端怎样处理平台拒绝 | [AuthController.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/AuthController.java) 的 `callback()` 接收 `GET /api/auth/callback`，`completeCallback()` 消费本次校验值后处理 `access_denied` |
| 怎样看到实际使用的本地编号 | [DemoController.java](../../backend/src/main/java/com/dcs4/ssoclient/demo/DemoController.java) 的 `me()` 对应 `GET /api/auth/me`，示例首页 [App.vue](../../frontend/src/App.vue) 显示返回的 `localUserId` |
| 怎么接到自己的页面和数据 | [InventoryApiController.java](../examples/InventoryApiController.java) 的 `inventory()` 演示接口先经过后端检查。实际系统随后根据本地用户编号加载角色、组织及数据权限 |
| 退出入口在哪里 | [AuthController.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/AuthController.java) 的 `logoutSystem()`、`logoutGlobal()` 对应当前客户端退出和全局退出 |

## 5. 部署地址与反向代理

以下是跨机部署示例。假设一体化平台和 Nginx（反向代理服务器）在 `192.9.230.24`，客户端实际服务在 `192.9.230.16:18085`。示例端口按现场替换。

| 项目 | 示例值 |
| --- | --- |
| 浏览器打开的客户端系统地址 | `http://192.9.230.24:18085` |
| 平台登记的系统地址 | `http://192.9.230.24:18085` |
| 平台登记的固定回调路径 | `/api/auth/callback` |
| 客户端配置的完整回调地址 | `http://192.9.230.24:18085/api/auth/callback` |
| Nginx 转发目标 | `http://192.9.230.16:18085`，保留原请求路径 |
| 平台认证接口前缀 | 由平台管理员提供，浏览器和客户端后端均需可达 |

在 `192.9.230.24` 的客户端入口上，将首页、静态资源、`/api/` 和业务页面请求转发给 `192.9.230.16`。回调应能直接到达客户端后端，回调后的页面和全局退出跳回的首页应留在同一个对外入口。生产使用 HTTPS（加密网页通信）时，登记和配置均使用浏览器看到的 HTTPS 地址，示例后端同时配置 `COOKIE_SECURE=true`。

在 Nginx 的站点配置中，可以按下面的方式转发客户端流量。示例采用内网 HTTP 地址帮助理解转发关系。

```nginx
server {
    listen 18085;

    location / {
        proxy_pass http://192.9.230.16:18085;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

整页登录跳转可以跨来源。只有前端脚本需要直接读取另一个来源的接口，或页面需要共享同一来源时，才需要专门处理同源问题。同源要求协议、主机和端口一致。只改为同一个 IP、仍开两个端口，浏览器依然会区分来源。示例中的首页、静态资源和绝对路径回跳以站点根路径为基础。若改成同一入口下的 `/client/` 前缀，应同步适配静态资源、业务路径、固定回调、会话标识发送范围和退出回跳。

上线前，检查代理、网关和应用日志。固定回调查询串会带一次性授权码与校验值。访问日志只记路径和必要的状态信息，例如在 Nginx 日志格式中用 `$uri` 记录路径。避免记录完整回调地址、认证请求正文或会话标识。

## 6. 接入完成后先核对这些结果

用示例验证本地账号识别与拒绝，再到业务系统核对实际角色和数据范围。解绑或换绑后，应打开受保护页面或调用业务接口触发校验。首页用户摘要只用于展示会话，最新的业务访问结果以受保护请求为准。

| 场景 | 预期结果 |
| --- | --- |
| 平台用户 `9001` 已绑定本地账号 `108`，且账号启用 | 示例登录后建立本地会话，首页显示编号 `108`。迁入业务系统后，再核对是否按 `108` 加载本地角色和数据范围 |
| 平台用户未绑定 | 平台拒绝给该客户端签发授权码。无需重新登录门户便可访问该用户有权使用的其他系统 |
| 有绑定，但本地账号已删除或停用 | 平台授权可通过，由客户端在建立本地会话前拒绝 |
| 解绑或换绑后继续使用原授权 | 后续核验发现原令牌失效，原本地会话应结束。重新授权时按最新绑定处理 |
| 仅退出客户端系统 | 本地会话清理，客户端后端向平台请求撤销本客户端授权。平台登录仍有效时，可重新进入一次授权流程 |
| 全局单点退出 | 平台登录状态失效，下次访问需重新登录并检查绑定与本地账号 |

如果所有用户都没有收到本地编号，先核对当前客户端是否启用了必绑、平台版本是否支持，以及客户端用户信息模型是否读取该字段。在授权阶段已被拒绝时，请管理员检查当前平台用户和客户端下的绑定。已经走完平台授权但无法进入业务页面时，再查本地账号是否存在、是否启用以及是否具有所需业务权限。
