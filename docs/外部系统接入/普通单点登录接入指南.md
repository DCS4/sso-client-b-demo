# 普通单点登录接入指南

适用于希望通过一体化平台登录，由客户端系统管理自己的页面、操作和数据权限的接入方。平台登记模式为 `SSO_ONLY`（普通单点登录），外部账号必绑关闭。

## 1. 开始前先认识三个组成部分

**一体化平台门户**提供统一登录页面。**平台认证服务**在用户登录后，根据客户端登记信息发放一次性授权码。**客户端系统**是要接入的业务系统，由它的后端接收授权码、核对身份并处理本地会话。随文提供的 **示例客户端**是一套用于练习和移植的代码。完整登录需要一个可用的一体化平台环境。

如果客户端系统可以按平台用户编号识别人员和归属业务数据，就直接使用该编号。如果已经有用户表、角色和历史数据，则继续使用本地账号，并由客户端系统维护平台用户编号与本地账号的对应关系。两种做法使用同一套登录和平台登记配置。

## 2. 由平台登记客户端

先与管理员确认平台门户和认证服务可用，并为本次测试使用独立的客户端登记。浏览器还需要能访问平台门户。

1. 接入方提供系统名称、浏览器访问的系统地址，以及一个固定回调路径。本例用 `http://localhost:18085` 和 `/api/auth/callback`。回调是登录完成后由浏览器访问的客户端后端入口。
2. 平台管理员创建并启用客户端，登记相应认证模式和上述地址，交付客户端编号 `client_id`、客户端密钥 `client_secret`、平台认证接口前缀和测试账号。
3. 登录测试前核对完整回调地址。例如 `http://localhost:18085/api/auth/callback` 必须与平台登记组合及客户端配置一致，包括协议、主机、端口和路径。客户端密钥由管理员创建或重置时取得，交给接入方后端负责人保管。

在平台选择普通单点登录，确认外部账号必绑关闭。这条路线无需向平台提交各业务页面清单或本地用户编号。已有账号体系时，由接入方准备至少一个已对应本地账号的平台测试用户，以及一个未对应的对照用户。

## 3. 先用示例走通登录

从仓库根目录将 `.env.example` 复制为 `.env`，已有 `.env` 时编辑现有文件。按 `键=值` 格式填写，替换下面的地址、编号和密钥示例。示例的浏览器导航和后端调用使用同一个 `SSO_BASE_URL`，两边都要能访问。把 `SSO_BASE_URL` 换成管理员提供的公共认证接口前缀，通常以 `/oauth2Server/oauth2` 结尾。认证接口地址与门户登录网页地址分别由管理员确认。

```properties
SSO_BASE_URL=http://localhost:19089/oauth2Server/oauth2
SSO_CLIENT_ID=替换为平台分配的客户端编号
SSO_CLIENT_SECRET=替换为平台交付的明文密钥
B_CALLBACK_URL=http://localhost:18085/api/auth/callback
SSO_AUTH_MODE=SSO_ONLY
SSO_REQUIRE_EXTERNAL_ACCOUNT=false
```

示例将真实密钥和平台访问令牌保存在后端。浏览器通过本地会话标识识别登录状态。一次性授权码和校验值会经过浏览器回调地址，由客户端后端处理。

运行示例需要 JDK 8、Maven 和符合 `frontend/package.json` 要求的 Node.js（22.18 起的 22.x，或 24.12 及以上）。在仓库根目录执行：

```powershell
.\scripts\package.ps1
java -jar backend/target/sso-client-b-demo-0.1.0-SNAPSHOT.jar
```

Linux 或 macOS 将第一条换为 `bash scripts/package.sh`。浏览器打开 `http://localhost:18085`，首页出现“业务系统 B”表示示例启动成功。点击业务页面才会开始与平台认证服务交互。把示例部署到别的机器时，回调中的 `localhost` 也要换成浏览器实际访问的主机。

点击【订单查询】。首次访问时，如果用户尚未登录平台，浏览器会进入平台登录页。登录成功后浏览器回到固定回调，再进入订单页。返回示例首页打开【经营报表】，系统级授权还有效时可以复用，两个页面仍各自经过后端的身份校验。示例保存平台身份供页面展示。真实系统可在同一个回调位置加入自己的身份处理。

## 4. 在已有业务系统中实现接入

### 4.1 先连接平台，再接入业务入口

| 改造位置 | 示例代码 | 需要实现的行为 |
| --- | --- | --- |
| 平台接口配置与调用 | `config/SsoConfig.java`、`sso/SsoClient.java` | 配置平台地址、客户端凭据和回调，从后端兑换授权码、核验和刷新令牌 |
| 登录入口与回跳目标 | `demo/PageController.java`、`auth/PageAccessService.java`、`auth/PageCatalog.java` | 在一个真实业务页面接入后端校验。缺少有效授权时，由后端记录受信任的业务目标并引导浏览器登录 |
| 固定回调与会话 | `auth/AuthController.java`、`auth/LoginStateStore.java`、`auth/PageTokenStore.java` | 验证一次性校验值，核对令牌和用户，建立自己的会话，回到原业务页面 |

这些路径都相对于 `backend/src/main/java/com/dcs4/ssoclient/`。接入方可用自己的框架实现相同行为。前端可以保留现有界面。

1. 页面或数据接口请求进入客户端后端。已有有效授权时检查身份，再执行本地业务权限。缺少有效授权时，后端生成 `state`（与当前会话绑定的一次性随机校验值），保存回跳目标并引导浏览器访问平台 `/authorize`。普通单点流程省略页面参数。
2. 固定回调接收 `code`（一次性授权码）和 `state`。后端先校验并消费 `state`，再用客户端密钥访问 `/token`。若平台回调返回拒绝，显示相应结果并结束本次登录。
3. 后端核对授权所属客户端和平台用户，再用 `/checkAccessToken` 确认令牌有效。随后通过 `/getUserInfoByOauth2` 取得用户资料。平台用户编号在用户资料的 `result.id` 中，应与授权结果的用户标识一致。
4. 按下节确定本地身份，成功后更新会话标识、保存服务端登录状态，并跳回服务端记录的页面。每次访问业务页面和接口时，按客户端自己的角色、组织和数据范围放行。

### 4.2 确定客户端系统识别用户的方式

- **直接使用平台用户编号。** 例如平台返回用户编号 `9001`，客户端系统以 `9001` 识别用户并关联自己的业务记录。适合新系统或已经以平台编号为业务依据的系统。客户端系统仍应决定这个用户可以使用哪些功能。
- **在客户端系统关联已有账号。** 例如张三的平台编号是 `9001`，本地账号编号是 `108`。在本地账号 `108` 上保存平台编号 `9001`，登录后按该编号查本地用户。仅在对应账号存在并启用时建立本地会话，继续以 `108` 查询原有角色、待办和数据。未开通时提示联系本系统管理员，或按接入方明确的开户流程处理。对应关系应在既定范围内唯一，使用稳定的编号匹配。

移植时将平台访问令牌放在服务端，在刷新时成对更新访问令牌与续期令牌。同一组令牌的刷新应按会话和授权范围串行执行。示例使用单实例内存会话。若客户端系统部署多实例，应让原始登录请求与回调能读到同一份登录状态，并处理并发刷新和节点故障后的重新授权。

认证服务超时或返回未知结果时，当前业务请求应返回错误，用户可以在服务恢复后重试。后端校验与前端展示应按同一个账号更新，切换账号时清理上一账号留在本地会话中的授权。

在现有前端中，页面入口可以通过浏览器整页跳转完成登录。数据接口需要登录时，可返回明确的状态及由后端生成的登录地址，由前端发起整页跳转。前端菜单、按钮及路由的可见性负责展示，业务接口的放行条件由后端执行。

### 4.3 接上退出入口

本地退出由客户端后端清理本系统会话，并用服务端保存的授权凭据向平台撤销本客户端相应授权。示例入口为 `POST /api/auth/logout/system`。全局退出可参考 `POST /api/auth/logout/global`，客户端先处理本地退出，再将平台退出地址交给浏览器整页打开。平台退出后的回跳地址应与已登记客户端地址同源。示例的提交请求带同会话的 CSRF 校验值，用于防止其他网站代替用户发起操作。

### 4.4 按请求顺序阅读示例代码

| 要找的环节 | 具体代码位置 |
| --- | --- |
| 业务页面如何触发登录 | [PageController.java](../../backend/src/main/java/com/dcs4/ssoclient/demo/PageController.java) 的 `page()` 接收 `GET /pages/orders` 等页面请求，再调用 `PageAccessService.enter()` |
| 后端怎样记住原页面 | [LoginStateStore.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/LoginStateStore.java) 的 `begin()` 保存本次请求，`consume()` 在回调时取出并删除 |
| 回调怎样建立会话 | [AuthController.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/AuthController.java) 的 `callback()` 接收 `GET /api/auth/callback`，再进入 [PageAccessService.java](../../backend/src/main/java/com/dcs4/ssoclient/auth/PageAccessService.java) 的 `completeCallback()`。已有本地用户表时，将按平台编号查本地账号的逻辑接在平台身份校验通过后、写入会话前 |
| 哪些方法调用平台 | [SsoClient.java](../../backend/src/main/java/com/dcs4/ssoclient/sso/SsoClient.java) 的 `authorizeUrl()` 生成授权地址，`exchangeCode()` 调用 `/token`，`checkAccessToken()` 核验授权，`getUserInfo()` 读取用户资料 |
| 为什么第二个页面能复用授权 | [SsoConfig.java](../../backend/src/main/java/com/dcs4/ssoclient/config/SsoConfig.java) 的 `tokenKey()` 在普通单点登录中返回同一个系统键，`enter()` 每次访问仍核验令牌 |
| 怎样在接口执行相同检查 | [InventoryApiController.java](../examples/InventoryApiController.java) 的 `inventory()` 演示在返回数据前进入后端检查，再加入本系统的数据和操作权限 |
| 前端怎样退出 | [App.vue](../../frontend/src/App.vue) 的 `logoutSystem()`、`logoutGlobal()` 分别调用本地退出和全局退出入口，[api.ts](../../frontend/src/api.ts) 的 `request()` 为提交请求携带校验值 |

## 5. 部署地址与反向代理

以下是跨机部署示例。假设一体化平台和 Nginx（反向代理服务器）在 `192.9.230.24`，客户端实际服务在 `192.9.230.16:18085`。示例端口按现场替换。

| 项目 | 示例值 |
| --- | --- |
| 浏览器打开的客户端系统地址 | `http://192.9.230.24:18085` |
| 平台登记的系统地址 | `http://192.9.230.24:18085` |
| 平台登记的固定回调路径 | `/api/auth/callback` |
| 客户端配置的完整回调地址 | `http://192.9.230.24:18085/api/auth/callback` |
| Nginx 转发目标 | `http://192.9.230.16:18085`，保留原请求路径 |
| 平台认证接口前缀 | 由平台管理员提供，浏览器和客户端后端均需可达 |

在 `192.9.230.24` 的客户端入口上，将首页、静态资源、`/api/` 和业务页面请求转发给 `192.9.230.16`。回调应能直接到达客户端后端，回调后的页面和全局退出跳回的首页应留在同一个对外入口。生产使用 HTTPS（加密网页通信）时，登记和配置均使用浏览器看到的 HTTPS 地址，示例后端同时配置 `COOKIE_SECURE=true`。

在 Nginx 的站点配置中，可以按下面的方式转发客户端流量。示例采用内网 HTTP 地址帮助理解转发关系。

```nginx
server {
    listen 18085;

    location / {
        proxy_pass http://192.9.230.16:18085;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

整页登录跳转可以跨来源。只有前端脚本需要直接读取另一个来源的接口，或页面需要共享同一来源时，才需要专门处理同源问题。同源要求协议、主机和端口一致。只改为同一个 IP、仍开两个端口，浏览器依然会区分来源。示例中的首页、静态资源和绝对路径回跳以站点根路径为基础。若改成同一入口下的 `/client/` 前缀，应同步适配静态资源、业务路径、固定回调、会话标识发送范围和退出回跳。

上线前，检查代理、网关和应用日志。固定回调查询串会带一次性授权码与校验值。访问日志只记路径和必要的状态信息，例如在 Nginx 日志格式中用 `$uri` 记录路径。避免记录完整回调地址、认证请求正文或会话标识。

## 6. 接入完成后先核对这些结果

下面核对的是接入方自己的业务系统。第 3 节的演示只展示平台身份和系统级授权。采用本地账号对应关系时，由接入方先完成第 4.2 节的账号查询和权限检查，再验证相关结果。

| 场景 | 预期结果 |
| --- | --- |
| 首次从业务入口访问 | 用户在一体化平台登录，回到原业务页面 |
| 同一会话切换业务页面 | 系统级授权可复用，客户端后端仍检查各页面和接口的本地权限 |
| 平台用户已登录，本地账号未开通或已停用 | 如果采用本地对应关系，由客户端系统拒绝建立本地会话。门户登录保持有效 |
| 已登录但没有本地业务权限 | 相应页面或数据接口拒绝访问 |
| 仅退出客户端系统 | 本地会话清理，客户端后端向平台请求撤销本客户端授权。平台登录仍有效时，重新进入可免输密码 |
| 全局单点退出 | 平台登录状态失效，再次访问受保护页面需要重新登录和授权 |

回调报“登录事务不存在、过期或已使用”时，先核对首次访问和回调是否经过同一客户端入口，并从业务页面重新开始。认证服务无法访问时检查接口前缀和后端网络；已有本地对应关系却仍被拒绝时再核对平台编号、本地账号状态及业务权限。
